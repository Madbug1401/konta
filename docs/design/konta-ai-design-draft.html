De gestor financeiro
a assistente financeiro.

O Konta continua a ser a infraestrutura — contas, transações, dívidas, metas, o Financial Engine. A IA é uma nova forma de chegar lá, não uma funcionalidade dentro dela.

A pergunta que este documento tenta responder
Como fazemos com que uma pessoa que normalmente não usaria um gestor financeiro consiga controlar a sua vida financeira simplesmente conversando com o Konta?
A · Visão final

Konta daqui a 1–2 anos

Não é "o Konta com um chat". É um assistente financeiro pessoal para o qual o Konta de hoje — contas, categorias, transações, dívidas, metas, o Financial Engine — passa a ser infraestrutura, não o produto em si. A interface manual não desaparece: torna-se a camada de confiança, auditoria e controlo fino que continua ali por baixo, sempre correta, sempre disponível para quem prefere ver e não falar.

Concretamente, sucesso daqui a 1–2 anos parece-se com isto: a maioria das interações do dia a dia — registar um gasto, perguntar quanto se pode gastar, criar uma meta, perceber porque as despesas subiram — acontece por linguagem natural, no mesmo sítio onde hoje está o dashboard. As páginas de Contas, Transações, Dívidas e Metas continuam a existir tal como estão, porque continuam a ser necessárias para três coisas que a conversa não substitui bem: auditoria (ver tudo, sem interpretação), correção de erros (editar um valor errado é mais rápido num formulário do que a explicar por palavras o que estava errado), e confiança inicial (algumas pessoas só confiam num número depois de o verem numa tabela).

Os dois invariantes que têm de sobreviver a todas as fases seguintes, sem exceção:

1 · A IA nunca é uma segunda fonte de verdade

Todo o número que a IA disser vem de uma chamada ao Financial Engine ou à base de dados — nunca de uma soma feita pelo próprio modelo. Isto já é assim para o Web e vai continuar a ser assim para a IA, o Mobile e qualquer cliente futuro.

2 · A interface manual nunca é removida

A IA é um caminho adicional para os mesmos dados e as mesmas ações, não um substituto. Um utilizador que nunca escreva uma frase ao Konta continua a ter uma aplicação completa.

Dentro desses limites, a visão final inclui capacidades que hoje não existem em lado nenhum do produto: planeamento financeiro guiado (não só "cria uma meta", mas "ajuda-me a chegar lá"), simulação de cenários ("e se eu poupar mais X?"), orçamento com acompanhamento real, análise de investimentos, e um assistente que nota coisas relevantes sem ser convidado a cada vez — mas todas estas capacidades entram por fases, com prova de confiança a cada passo, nunca todas de uma vez. É esse faseamento que as secções B e I detalham.

B · V1

A menor fatia real da visão final

O objetivo da V1 não é "um chat pequeno e simples". É provar, de ponta a ponta, com dados reais e utilizadores reais, o ciclo completo que sustenta tudo o resto: intenção → interpretação → proposta → confirmação → execução → explicação. Cada peça da V1 já é uma instância real de uma capacidade final, só que na sua forma mais estreita — não é uma versão de brincar que será deitada fora.

Tool na V1O que prova hojeEm que cresce depois
create_transactionInterpretar uma frase de gasto/receita ambígua e transformá-la numa transação real, validada pelas mesmas regras de sempre.update_transaction, transferências faladas, deteção de duplicados
create_goalLigar uma intenção ("quero comprar X até março") a um plano com números reais do Financial Engine por trás.update_goal, contribute_to_goal, replaneamento automático
analyze_financesCompor vários cálculos já existentes (cashflow, poupança, categorias) numa resposta explicada, não numa tabela.comparação entre períodos, deteção de anomalias, insights on-open
get_accounts / get_transactions / get_debts / get_goalsResponder a perguntas de leitura sem o utilizador navegar nada.continuam praticamente iguais — já são o desenho final

"Feito" para a V1 significa, sem ambiguidade: as sete tools acima a funcionar em produção, cada escrita sempre com confirmação explícita, cada chamada registada num log de auditoria, um limite diário de custo por utilizador ativo desde o primeiro dia, e nenhuma linha de validação nova — só reutilização do que já existe em src/lib/db e src/lib/financial-engine.

C · Agent Architecture

Como um pedido atravessa o sistema

Proposta de camadas — não é a única forma correta de desenhar isto, é o ponto de partida para discutirmos. A ideia central: cada camada tem uma responsabilidade e nenhuma faz o trabalho da seguinte.

Porque estas camadas e não outras

AI Gateway é o único sítio que fala com a API da Anthropic — isto importa para custo (é onde o limite diário é verificado antes de gastar um token) e para segurança (nunca outro sítio do código constrói um pedido para a Claude API por engano).

Context Builder existe separado do Gateway porque a decisão "que dados enviar" é, por si só, uma decisão de privacidade e de custo que merece ser testada isoladamente — ver secção F.

Tool Registry é só dados: uma lista de tools com o seu schema Zod, o texto humano que descreve o que fazem, e o nível de risco. Não tem lógica. É o que torna a lista de ferramentas do ponto 3 da tua mensagem uma coisa que cresce por configuração, não por reescrita.

Permission Layer é a peça nova que a tua pergunta sobre níveis de risco pede — e é deliberadamente separada do Tool Executor. Isto quer dizer que amanhã, quando quiseres que create_transaction passe a ser LOW para valores pequenos e categorias habituais, a mudança acontece só aqui, nunca na tool em si.

Conversation State e AI Action Log são deliberadamente dois armazenamentos diferentes, não um só: o primeiro é descartável (a conversa de agora), o segundo é permanente e é auditoria (o que foi feito, quando, com que risco, a que custo).

D · Tool Architecture

Uma tool é um contrato fino, não lógica nova

A regra que evita reconstruir o agente mais tarde: uma tool nunca contém a regra de negócio — só a aponta. Cada tool é um pequeno módulo com quatro partes, e as quatro já têm equivalente direto no código existente.

paramsSchema

O mesmo Zod que já existe

Ex: a tool create_transaction não inventa uma validação nova — importa e reutiliza literalmente o CreateTransactionSchema já definido em src/app/api/transactions/route.ts. Um pedido inválido é recusado da mesma forma, quer venha de um formulário ou de uma frase.

execute(userId, params)

A mesma função do backend

Chama diretamente createTransaction() de src/lib/db/transactions.ts — a mesma função que o Server Component do dashboard e a rota de API já chamam hoje. Continua a valer "uma única implementação de cada regra financeira, vários pontos de entrada" — a IA é só o terceiro ponto de entrada.

riskTier

Metadado, lido pela Permission Layer

Não é lógica — é uma etiqueta (LOW / MEDIUM / HIGH / CRITICAL) que outra camada consulta. Isto é o que permite mudar o comportamento de risco sem tocar na tool.

summarize(params)

A frase de confirmação

Gera o texto humano que o utilizador vê antes de confirmar — "Vou registar uma despesa de 750 CVE em Alimentação, na Carteira, hoje." Nunca é o próprio modelo a inventar essa frase à solta; é um template controlado por nós, alimentado pelos parâmetros já validados.

O Tool Registry é simplesmente a lista de todas estas tools — hoje sete, no futuro vinte ou mais — exposta ao Claude como definições de tool-use, e usada pela Permission Layer para decidir o nível de confirmação. Adicionar pay_debt_installment mais tarde é: um novo ficheiro em src/lib/ai/tools/, reaproveitando payInstallment() de src/lib/db/debts.ts (que já corre dentro de uma transação SQL com FOR UPDATE), com riskTier: "HIGH". Nenhuma outra camada muda.

Porque isto não obriga a reconstruir nada depois

O Gateway, o Context Builder e a Permission Layer não sabem — nem precisam de saber — quantas tools existem ou o que cada uma faz. Só percorrem o Registry. Passar de 7 para 20 tools é um problema de conteúdo, nunca de arquitetura.

E · Permission System

Risco por chamada, não só por tool

A ideia mais importante desta secção: o nível de risco não tem de ser fixo por tool para sempre. Pode (e deve, na visão final) depender também dos parâmetros de cada chamada — um create_transaction de 500 CVE numa categoria habitual não é o mesmo risco que um de 90.000 CVE numa categoria nunca usada. Para a V1, achatamos essa nuance de propósito: toda a escrita é HIGH, sem exceção. A arquitetura já suporta o cálculo fino — só ainda não o usamos.

NívelExemploComportamento na V1Comportamento futuro
LOWLer saldo, listar transações, "quanto posso gastar hoje"Executa sempre — nunca escreve nadaIgual — leitura nunca precisa de confirmação
MEDIUMRegistar 500 CVE de transporte, categoria habitual, valor típicoTratado como HIGH nesta faseConfirmação rápida (um toque), sem resumo alargado
HIGHCriar uma meta, criar uma dívida, pagar uma parcela, um valor fora do padrãoConfirmação explícita, com resumo dos parâmetrosIgual — continua sempre a exigir confirmação
CRITICALEliminar dados, mudar definições de conta, qualquer coisa fora do que um humano já pode fazer na UIRecusado — nem chega a proporContinua recusado — o Konta nunca deu isto a um humano, não dá a uma IA

O mecanismo concreto de "subir de nível" não é uma decisão nossa arbitrária mais tarde — é orientado pelos próprios dados do AI Action Log: se, ao fim de algumas semanas, uma fatia grande das confirmações de create_transaction for aceite sem qualquer alteração, isso é o sinal (não uma opinião) de que vale a pena deixar valores pequenos, em categorias já usadas, passarem a MEDIUM. É uma promoção ganha pelo comportamento real do utilizador, não concedida de início — voltamos a isto na secção I.

F · Context

O AI Context Builder — enviar o mínimo, nunca a base toda

Regra arquitetural, não preferência: nenhum pedido ao Claude carrega transações em bruto por omissão. O Context Builder classifica primeiro a intenção (um passo barato, quase sempre um modelo pequeno ou até heurística simples) e escolhe um de três pacotes de contexto.

leve

"Quanto gastei este mês?"

Só os totais já agregados do mês corrente por conta/moeda — números que o Financial Engine já calcula para o dashboard. Não precisa de nenhuma transação individual.

completo

"Analisa as minhas finanças."

O resumo alargado: cashflow, poupança, categorias do mês vs. anterior, metas ativas com progresso, dívidas com próximas parcelas — tudo já calculado, nunca uma lista de transações linha a linha.

dirigido

"Que gastos tive na sexta?"

Só aqui uma tool de leitura específica (get_transactions com filtro de data) é chamada, buscando exatamente essas linhas — nunca antecipadamente, só quando o pedido concreto precisa.

Falar de privacidade sem destruir confiança

A página /help promete hoje "os teus dados são só teus" — e isso continua verdadeiro no sentido em que sempre foi (ninguém mais na plataforma os vê). Mas passa a haver um processamento por um terceiro (a Anthropic) que hoje não existe, e isso merece ser dito em português simples, uma vez, no momento em que a pessoa abre o assistente pela primeira vez — não escondido nos termos de serviço.

Proposta de texto — primeira abertura do assistente

"As tuas mensagens e um resumo dos teus dados financeiros são processados pela Anthropic (a empresa por trás do Claude) para gerar respostas. O Konta nunca envia o histórico completo das tuas transações — só o que é preciso para responder ao que perguntaste."

G · Cost

Desenhado para um cartão com 592 CVE, não para escalar primeiro

A pergunta que puseste — "quanto custa, em média, uma interação" — não deve ser respondida com uma estimativa hoje. Deve ser respondida por um número real, medido, ao fim de poucos dias de uso real. O papel da arquitetura é garantir que esse número existe e nunca foge de controlo entretanto.

Antes de gastar um token

O AI Gateway verifica o limite diário do utilizador e um limite global antes de sequer construir o pedido. Sem exceção — nem para o dono do projeto.

Modelo certo para cada pedido

Um modelo mais pequeno e barato para classificar a intenção e extrair campos de frases simples ("gastei X em Y"); o modelo maior reservado para análise aberta e planeamento, onde o raciocínio compensa o custo.

Contexto mínimo (secção F)

É também, em si, a maior alavanca de custo: um resumo calculado tem uma fração dos tokens de um histórico de transações em bruto.

Prompt caching

O prompt de sistema e as definições de tools são praticamente estáticos entre pedidos — candidatos naturais a cache, o que reduz o custo repetido da parte mais pesada e mais previsível de cada chamada.

Concretamente: uma tabela nova, AiUsageLog, grava por cada turno o utilizador, os tokens de entrada/saída e o modelo usado. Uma página interna — no mesmo espírito de /admin, que já existe só para o dono do projeto ver totais sem tocar em dados privados de ninguém — mostra o custo médio real por interação, o total do dia e do mês. É essa página, não uma conta feita à mão, que te diz quando faz sentido aumentar o crédito. Quando o limite é atingido, a resposta é sempre clara e imediata — "chegaste ao limite de hoje, usa a app normalmente ou tenta amanhã" — nunca uma falha silenciosa nem uma cobrança inesperada.

I · Roadmap

V1 → V2 → V3 → Agente completo

Cada fase só avança com o que a anterior provou — nunca com o que parecia uma boa ideia entretanto.

FASE 1

V1 — provar o ciclo

Entra
  • 7 tools (4 leitura + create_transaction + create_goal + analyze_finances)
  • Confirmação obrigatória em toda a escrita
  • AiActionLog + AiUsageLog
  • Limite diário por utilizador e global
Fica de fora
  • update_*, pay_debt_installment
  • Proatividade
  • Memória de longo prazo
FASE 2

V2 — completar o ciclo de vida

Entra
  • update_transaction, update_goal, update_debt, pay_debt_installment
  • calculate_savings_plan, simulate_financial_scenario (Web)
  • Primeira promoção de risco: MEDIUM real, orientada pelo AiActionLog
Fica de fora
  • Orçamento persistente
  • Onboarding guiado pela IA
FASE 3

V3 — planeamento e proatividade

Entra
  • Orçamento como entidade real (se validado como querido)
  • Análise de investimentos assistida
  • Insights ao abrir a app — nunca push
  • Onboarding financeiro conduzido pela IA
Fica de fora
  • Cadeias autónomas multi-passo
  • Voz
FASE 4

Agente completo

Entra
  • Planeamento multi-passo supervisionado
  • Memória de preferências — explícita, visível, editável pelo utilizador
  • Voz no Mobile
  • Notificações proativas reais, com opt-in próprio
Para fechar — como Product Strategist

A fricção não desaparece por decreto. Compra-se com confiança.

Uma pessoa que hoje não usaria um gestor financeiro não vai mudar de ideias porque passou a poder escrever em vez de clicar — muda porque a primeira frase que escreveu produziu, sem esforço nenhum de configuração, um resultado correto, visível e explicado. Esse é o momento que a V1 tem de garantir: não a mais ampla lista de tools, mas a certeza absoluta de que create_transaction nunca engana ninguém.

A partir daí, a redução de fricção — automatizar o que hoje pede confirmação, ser proativo sem ser convidado — não é uma promessa do dia 1. É algo que o produto ganha, utilizador a utilizador, medido pelo próprio comportamento registado no AI Action Log. É esse o fio que liga a arquitetura de permissões (secção E) à estratégia de produto: confiança não se assume, prova-se, e a arquitetura já está desenhada para guardar a prova.
