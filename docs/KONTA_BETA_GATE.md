# KONTA — BETA GATE

**Data**: 29/08/2026
**Ponto de partida**: `docs/GO_TO_BETA_AUDIT.md` (29/08/2026), veredito original **NOT BETA READY**, com uma lista curta de 6 pontos de risco real (secção 19 desse documento) mais uma lista adicional de 12 prioridades de hardening definida pelo utilizador para esta tarefa.
**Método**: cada uma das 12 prioridades foi implementada, testada com um teste automático dedicado quando fazia sentido, e verificada de facto (não só por inspeção de código) — contra um Postgres 16 real e/ou um servidor HTTP real corrido a partir do build de produção, incluindo simulações reais de ataque (ownership de categoria, base de dados indisponível, backup/restore ponta-a-ponta). No final: `npm run build`, `npx tsc --noEmit`, `npx eslint .` e `npx vitest run` — os quatro a passar sem erros, 61 testes.

---

## Corrigido

**1. Backup automatizado do Postgres** — não existia nenhum (só o volume Docker, que o audit já tinha rejeitado como backup real). Criados `scripts/backup/backup.sh` (dump diário, retenção de 14 dias, cópia opcional para armazenamento externo via `rclone`), `restore.sh` (restauro com `--clean --if-exists`, exige `--yes` explícito) e `verify-backup.sh` (restaura para uma base de dados temporária e descartável e confirma dados legíveis, não só a existência do ficheiro). O ciclo completo — dump real, restauro real, verificação real, e substituição correta de dados existentes — foi executado de facto contra um Postgres 16 real nesta tarefa (não apenas escrito e assumido). Documentado em `docs/architecture/BACKUP.md`.

**2. Resiliência da ligação à base de dados** — `pg.Pool` sem `pool.on('error', ...)` significava que qualquer soluço de rede transitório derrubava o processo Node inteiro. Corrigido em `src/lib/db/client.ts`; teste de regressão (`client.test.ts`) emite o evento `'error'` diretamente e confirma que o processo não morre. Verificado também com uma base de dados real desligada a meio de um pedido HTTP.

**3. Rate limiting em login/registo** — sem qualquer proteção contra força bruta. Implementado um limitador em memória por janela fixa (`src/lib/rate-limit.ts`, sem nova dependência), 10 tentativas/15min em `/api/auth/login`, 5/hora em `/api/auth/register`, resposta 429 com `Retry-After`. Decisão documentada de não usar CAPTCHA para esta Beta (poucos utilizadores, todos conhecidos do lançamento inicial) — ver `DECISIONS.md`.

**4. Tratamento de erros e mensagens ao utilizador** — várias rotas deixavam exceções não tratadas rebentar como 500 cru; zero `error.tsx`/`global-error.tsx` no App Router. Criado `withErrorHandling` (`src/lib/api-error.ts`), aplicado às 8 rotas de API; mensagem genérica fixa **"Algo correu mal. Tenta novamente."** nunca expõe stack trace nem detalhe técnico ao utilizador; o erro técnico completo é sempre registado no lado do servidor. `error.tsx` e `global-error.tsx` adicionados como redes de segurança para falhas de Server/Client Component.

**5. Logging mínimo** — zero logging em toda a aplicação (confirmado pelo audit original). Criado `src/lib/logger.ts` (`logError`/`logInfo`), com o tipo `LogMeta` deliberadamente restrito a valores primitivos simples — para tornar estruturalmente difícil (não só "lembrar de não fazer") registar passwords, hashes, tokens, cookies ou dados financeiros completos por engano. Usado no pool de base de dados, no health check e em todas as rotas via `withErrorHandling`.

**6. Health check** — não existia `/api/health`. Criado `GET /api/health`, sem autenticação, corre `SELECT 1` na base de dados real, devolve 200 quando saudável e 503 quando não, sem expor nenhum dado sensível no corpo da resposta. Verificado com a base de dados a funcionar (200) e desligada (503) de facto, não só por leitura do código. `docker-compose.prod.yml` já aponta o healthcheck do serviço `app` para este endpoint.

**7. Ownership de `categoryId`** — o audit encontrou que, ao contrário de `accountId`/`destinationAccountId`, um `categoryId` de outro utilizador era aceite sem verificação ao criar/editar uma transação (falha de BOLA — Broken Object Level Authorization). Corrigido com `getCategoryById(userId, categoryId)`, seguindo exatamente o mesmo padrão já usado para contas. Verificado com um ataque real: uma segunda conta de utilizador tentou associar uma transação à categoria da primeira, contra dados reais no Postgres — rejeitado corretamente após a correção (e confirmado que sem a correção o ataque tinha sucesso).

**8. Validação de `limit`/`offset` em `GET /api/transactions`** — valores inválidos (`NaN`, negativos, absurdamente grandes) rebentavam como 500 não tratado. Criado `parsePagination` (`src/lib/pagination.ts`, 11 casos de teste), devolve 400 limpo para qualquer input inválido, com limites (`MAX_LIMIT=200`, `MAX_OFFSET=1_000_000`) para impedir consultas desproporcionadas.

**9. Normalização de email** — `Test@Example.com` e `test@example.com` registavam-se como duas contas distintas. Corrigido centralizando `normalizeEmail` (trim + lowercase) dentro de `findUserByEmail`/`createUser` em `src/lib/db/users.ts` — qualquer chamador futuro herda a correção automaticamente. Verificado de facto: registo com maiúsculas seguido de login com minúsculas (e vice-versa) autentica na mesma conta; segunda tentativa de registo com capitalização diferente do mesmo email é corretamente rejeitada como duplicado.

**10. Política de eliminação de dados (ON DELETE) documentada** — o audit identificou `Transaction.accountId ON DELETE CASCADE` como risco (apagar uma conta apagaria o histórico financeiro real). Catalogadas todas as 17 chaves estrangeiras do schema em `docs/architecture/DELETE_POLICY.md`; decisão registada de que uma futura funcionalidade de eliminação de conta deve usar o campo `Account.isArchived` (já existente no schema, nunca usado) em vez de `DELETE` físico, e recomendação de migrar essa constraint para `RESTRICT` quando essa funcionalidade for construída. **Nenhuma funcionalidade de delete foi implementada** — tarefa exclusivamente de documentação, por pedido explícito.

**11. Correções pequenas de UX** — sem redesign, por pedido explícito. `EmptyState` sem contas ganhou ação (`AccountForm`) nas três páginas onde faltava (Dashboard, Contas, Nova Transação — esta última era um beco sem saída antes); labels acessíveis adicionadas à barra de filtros de transações (`sr-only`, sem alterar o layout visual) e ao formulário de contas (padrão visível já usado no formulário de transações); botões de editar/remover transação aumentados de 36×36px para 44×44px (alvo de toque mínimo recomendado). Verificado com screenshots reais contra o build de produção corrido localmente, autenticado via API real.

**12. Estratégia de deployment documentada** — decisão justificada (não por preferência) de um único VPS + Docker Compose em vez de uma plataforma gerida, com os critérios explicados em `docs/architecture/DEPLOYMENT.md`; `Dockerfile` multi-stage (`output: "standalone"`), `.dockerignore`, `docker-compose.prod.yml` (Postgres + app, healthcheck ligado à Prioridade 6), `.env.production.example`, processo de migração e arranque documentado ponta-a-ponta. O `docker build` real não pôde ser corrido neste sandbox (registo `docker.io` bloqueado pela política de rede do ambiente de desenvolvimento — a mesma limitação já documentada para o Prisma) — verificado indiretamente com sucesso: `npm run build` gera exatamente os artefactos que o `Dockerfile` espera copiar, e correr `.next/standalone/server.js` diretamente serve HTTP 200 real em `/login`.

Adicionalmente, corrigido nesta base (herdado do audit, não uma prioridade nova): o bug crítico de auto-transferência (uma transferência de uma conta para si própria inflacionava o saldo do utilizador) permanece corrigido e testado.

## Aceito como limitação

Limitações conscientemente aceites para uma Beta de 10–30 utilizadores, todas documentadas em `docs/architecture/DECISIONS.md`:

- **Rate limiting em memória, de uma só instância.** Correto e suficiente para a decisão de hosting escolhida (um único VPS); não sobreviveria a múltiplas instâncias da app sem estado partilhado (ex: Redis) — só relevante se a Beta crescer muito além de 30 utilizadores.
- **Sem CAPTCHA.** Decisão explícita, documentada — poucos utilizadores na Beta, todos conhecidos do lançamento inicial; o rate limiting já corta força bruta automatizada.
- **Sem mecanismo de revogação de sessão** (JWT de 30 dias sem `jti`/denylist) — já identificado como aceitável para depois da Beta no audit original; não alterado por não estar nas 12 prioridades desta tarefa.
- **Logging mínimo, não observabilidade a sério** (sem Sentry/métricas/tracing) — exatamente o que foi pedido; suficiente para saber que algo correu mal e com que erro, não para diagnosticar tendências a longo prazo.
- **Dívidas, Metas, IA, Open Banking, Stripe, mobile nativo, CORS, Prisma real, migração do localStorage** — todos fora de âmbito por decisão explícita do utilizador, não avaliados nesta tarefa.
- **Sem teste de integração automatizado ponta-a-ponta para isolamento entre utilizadores** — cada correção relevante (ownership de categoria, normalização de email, paginação) tem teste automático dedicado, e o ataque de ownership foi verificado manualmente contra dados reais; continua a não existir uma suite de integração que corra isto em CI a cada alteração futura. Aceitável para o tamanho desta Beta, mas é a próxima peça de qualidade óbvia.
- **Backup local com retenção de 14 dias; destino externo (`rclone`) documentado mas não configurado com um destino real** — protege hoje contra corrupção do volume Docker/disco local; a proteção contra "o servidor inteiro desaparece" só fica ativa quando um `RCLONE_REMOTE` real for configurado no VPS de produção (não pode ser feito dentro deste sandbox, que não tem um VPS real nem credenciais de um destino externo).
- **`docker build` real não executado neste ambiente** — bloqueado pela política de rede do sandbox (mesma classe de limitação já documentada para o Prisma). Verificado indiretamente com sucesso (ver acima); a suposição por trás desta aceitação é que o `Dockerfile` segue o padrão oficial do Next.js e que `npm run build` já confirma que os artefactos que ele copia existem e funcionam — mas a primeira construção real da imagem deve acontecer numa máquina com acesso a `docker.io` antes de depender dela para a Beta.

## Ainda bloqueia Beta

Estes não são problemas de código nem de arquitetura — são passos de infraestrutura real que só podem ser executados quando existir um servidor de produção real, e que este ambiente de desenvolvimento sandboxed não tem como executar por si. Nenhum está pendente por falta de decisão: todos já têm a decisão e o procedimento documentados (`DEPLOYMENT.md`, `BACKUP.md`); falta é executá-los, uma vez, no servidor real, antes de dar acesso a qualquer utilizador da Beta.

1. **HTTPS/TLS em frente da aplicação.** `NODE_ENV=production` liga o cookie de sessão como `secure` (correto: sem isto, um cookie de sessão viajaria em texto claro em qualquer rede). Mas isso significa que, sem HTTPS a funcionar de facto no servidor, **nenhuma sessão consegue persistir** — o login parece funcionar e desaparece de imediato. Isto não é uma melhoria de segurança opcional: sem TLS configurado, a aplicação não funciona minimamente em produção para utilizadores reais. Duas opções documentadas em `DEPLOYMENT.md` (proxy reverso com Caddy/Nginx+Certbot, ou TLS gerido pelo fornecedor de VPS) — nenhuma delas foi implementada, porque nenhuma faz sentido sem um domínio e um servidor real à frente.
2. **Confirmar `docker build` completo numa máquina com acesso real ao Docker Hub** (o próprio VPS de produção, ou qualquer portátil) — antes de depender do `Dockerfile` para a Beta. A verificação indireta feita nesta tarefa é sólida, mas não substitui correr o comando real uma vez.
3. **Agendar `backup.sh` (+ `verify-backup.sh`) no `cron` do servidor real**, e **configurar um `RCLONE_REMOTE` real** para o destino externo. Sem isto, o mecanismo de backup existe e está testado, mas não está *ativo* — é código pronto, não proteção em produção.
4. **Gerar `AUTH_SECRET` e `POSTGRES_PASSWORD` novos para produção**, nunca os valores de desenvolvimento — mecânico, mas teria consequências sérias se esquecido.
5. **Correr um ciclo real de backup → restauro no ambiente de produção real** (`docker compose exec`, não os comandos equivalentes usados neste sandbox) pelo menos uma vez, antes do primeiro utilizador real entrar — para fechar a única diferença entre "verificado com comandos equivalentes" e "verificado no sítio exato onde vai correr".

Nenhum destes é trabalho de programação — é uma checklist mecânica de arranque em produção, esperada para qualquer aplicação que passe de "corre no meu portátil" para "corre num servidor real", da ordem de horas, não de dias. Mas enquanto não estiverem feitos, abrir a Beta a 10–30 pessoas reais teria pelo menos um problema imediato garantido (sessões que não persistem, por causa de #1) e um risco de dados sem rede de segurança real (por causa de #3).

## Estado final

**NOT BETA READY — mas por uma checklist de arranque em produção, não por dívida de código.**

Todos os riscos que o `GO_TO_BETA_AUDIT.md` classificou como bloqueadores ou de alta prioridade ao nível de código e de lógica de produto foram corrigidos, testados com testes automáticos dedicados, e verificados de facto contra dados e servidores reais sempre que o ambiente o permitiu: resiliência a falhas de rede da base de dados, força bruta, tratamento de erros, ausência de logs, health check, BOLA em `categoryId`, validação de paginação, duplicação de contas por email, e a decisão sobre eliminação de dados. `npm run build`, `npx tsc --noEmit`, `npx eslint .` e `npx vitest run` passam sem nenhum erro — mas, como pedido explicitamente, isso não é por si só motivo para declarar Beta pronta: passar testes prova que o código faz o que os testes descrevem, não que a infraestrutura à volta dele existe.

E não existe: este trabalho foi feito inteiramente dentro de um sandbox de desenvolvimento sem VPS real, sem acesso ao registo Docker, sem domínio, sem certificado TLS. A aplicação, tal como está agora, **não pode ser exposta a 10–30 utilizadores reais hoje** — não por um bug, mas porque, sem HTTPS configurado no servidor real, as sessões de login nem sequer persistem, e sem o cron de backup agendado no servidor real, a proteção contra perda de dados existe como código testado mas não como proteção ativa.

A distância até **BETA READY** é agora pequena e mecânica, não um problema de produto: os 5 pontos da secção "Ainda bloqueia Beta" acima, todos executáveis num único dia de trabalho de infraestrutura num VPS real, seguindo exatamente os procedimentos já documentados em `DEPLOYMENT.md` e `BACKUP.md`. Depois de os fazer — e de confirmar `GET /api/health` a devolver 200 através do domínio real com HTTPS —, o Konta passa a **BETA READY com as limitações listadas em "Aceito como limitação"**, que são razoáveis e conscientes para uma primeira Beta pequena e não escondem nenhum risco novo.

**Recomendação de sequência**: (1) provisionar o VPS e confirmar `docker build`; (2) configurar TLS; (3) subir `docker-compose.prod.yml` com segredos novos; (4) agendar backup + configurar `RCLONE_REMOTE`; (5) correr um ciclo real de backup/restauro; (6) confirmar `/api/health` via HTTPS; só depois disso, abrir a um grupo pequeno de confiança (2–3 pessoas) antes dos 10–30 utilizadores da Beta completa — a mesma recomendação de faseamento do audit original, que continua válida.
